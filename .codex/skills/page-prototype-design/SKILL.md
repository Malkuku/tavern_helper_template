# Page Prototype Design

页面原型首先解决用户要看什么、判断什么、操作什么；已有页面或原型存在时，优先在其基础上演进，不擅自重新设计。

## 基本流程

1. 明确页面角色、首屏主问题和核心动作。
2. 读取已有页面、原型和相关 API/数据契约。
3. 区分：
   - 必须保留的现有结构与视觉；
   - 当前任务明确要求修改的部分；
   - 因业务或工程实现必须补充的内容。
4. 校准信息层级、交互语义和契约边界。
5. 原型进入正式前端实现时，再按业务职责拆分组件、状态和数据流。

需要详细设计判断时读取 `DESIGN.md`；需要研究参考页面时读取 `REFERENCE.md`。

## 参考与修改原则

如果用户提供已有页面、HTML 原型、截图或明确参考对象：

- 默认视为需要**保留的设计基线**，不是重新设计邀请。
- 保留未被任务要求修改的布局、信息结构、视觉层级和交互模式。
- 只修改任务需要改变的部分，以及为修复明显逻辑缺口所必需的内容。
- 不因为存在“更合理”“更现代”或个人偏好的方案，就整体替换现有设计。
- 如果确实需要大范围重构，先明确指出原因和影响，不静默重写。

“参考某页面”也不等于复制视觉。应明确哪些结构采用、哪些按业务改造、哪些不适用。

## 页面设计

先判断页面职责，例如工作台、列表、详情、统计、输入或聊天。

每个主要区域都应服务于用户当前需要回答的问题或执行的动作。优先用空间和结构表达层级，再使用颜色、标签和说明文本。

注意：

- 展示、导航、筛选和直接操作应有明确语义；
- 看起来可点击的元素必须承担实际动作，否则表现为静态状态；
- 核心业务动作必须可见，不用说明面板代替操作入口；
- 不为了丰富页面添加没有业务来源的字段或模块；
- AI 摘要、规则说明等只有能帮助用户决策或行动时才进入核心区域。

## 数据与契约

原型字段分为：

- **契约字段**：已有 API/数据模型支持，可进入真实编辑和保存流程；
- **派生展示**：由已有数据计算，只用于显示；
- **待契约能力**：当前后端没有支持，只能显式标记为待实现，不伪装成已可保存功能。

静态原型允许 mock 数据，但应保持字段结构和正式数据来源可映射。

不要为了填满详情、抽屉或卡片而虚构字段。

## 原型落地到正式前端

HTML/CSS 原型描述的是**设计结果**，不是正式组件结构。

落地到 Vue、React 等工程时：

- 先读取现有页面结构、组件体系、状态管理、请求层和项目约定；
- 按业务职责识别页面区块和组件边界；
- 将 mock 数据替换为真实 props、state、store、API 或派生数据；
- 将静态交互转换为真实事件、状态流转、路由和请求行为；
- 复用项目已有组件和基础设施，不为还原原型重复实现已有能力。

禁止为了“还原原型”：

- 把整份 HTML 直接塞进单个页面组件；
- 把大块 mock 数据长期写死在正式组件中；
- 忽略明显存在的业务模块边界；
- 用静态文本模拟本应由 Vue 状态或 API 驱动的行为；
- 为方便复制原型而绕开已有组件、请求层或状态管理。

**视觉结构应尽量忠实于已确认原型，工程结构则应按正式项目重新组织。**

## 修改范围

静态 HTML/CSS 原型调整默认只验证原型本身，不运行完整正式构建。

修改正式 Vue/React 源码时，应同时检查：

- 页面结构是否仍符合已确认原型；
- 数据是否来自正确业务来源；
- 组件拆分是否符合已有项目结构；
- 核心交互是否真正工作；
- 是否残留仅供原型使用的 mock、占位逻辑或静态状态。

不要借页面修改顺手重构与任务无关的现有实现。
