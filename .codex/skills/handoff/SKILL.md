# Handoff

Handoff 是交给另一个执行上下文继续完成任务的临时交接单，不是长期项目事实源。

接收方可能是：
- 无法访问发送方内容的独立工作区；
- 能访问同一工作区文件，但没有当前 Chat 历史的新 Chat 或 agent。

## 交接模式

先判断接收方能访问哪些上下文。

### 独立上下文

接收方无法访问发送方工作区、Spec、代码或历史对话时，Handoff 必须自包含：

- 直接写出跨边界契约、结果和必要背景；
- 不依赖发送方内部路径才能理解任务；
- 不猜测接收方的文件、组件或实现位置。

### 共享工作区

接收方能访问同一工作区，只缺少当前对话上下文时：

- 优先引用工作区内已有 Spec、API、任务或代码事实，避免重复搬运；
- 补充这些正式材料中没有记录、但完成当前任务必须知道的决策和约束；
- 明确指出接收方应从哪些现有工件继续。
- 不把完整聊天过程写进 Handoff。

无论哪种模式，接收方都必须能明确知道：**为什么交接、要做什么、必须保持什么、如何验收。**

## 使用边界

仅在任务需要跨执行边界继续承接时使用，例如：

- 前后端、设计、运维或共享协议之间同步变化；
- 一个工作区产生的契约需要另一个工作区实现；
- 当前 Chat 的工作需要交给同项目的新 Chat 或 agent 继续。

不用于：
- 完全封闭在当前执行上下文的任务；
- 单纯总结当前对话；
- 已有双方可访问且内容完整的正式任务，无额外交接信息需要补充。

长期知识应进入 Spec、ADR、API、迭代任务、代码或测试，而不是 Handoff。

## 文件

默认维护当前工作区根目录：

`HANDOFF.md`

写入前先读取已有文件：

- 同一次交接：更新；
- 已完成或无关：替换；
- 不在一个文件中混合互不相关的接收方任务。

多个独立接收方应分别生成面向各自任务的 Handoff。

## 内容原则

只写接收方完成任务需要的信息。

优先包含：
- 必要背景；
- 契约、行为或结果变化；
- 接收方需要完成的修改；
- 必须保持的兼容行为和范围边界；
- 接收方可独立验证的验收标准。

避免：
- 发送方完整实现过程和 agent 分工；
- 与接收方无关的内部修改；
- 无意义复制正式文档；
- 无依据猜测接收方实现细节。

字段、接口、枚举或行为变化时，优先使用修改前 / 修改后的差异表达，并注明默认值、空值、兼容方式、版本或部署顺序等必要语义。

任务不能只写“同步”“适配”“保持一致”，应明确到接收方能够定位需要修改的功能边界。

## 最小结构

```md
# Handoff

## 交接目标
- 来源：
- 接收方：
- 任务主题：

## 背景
...

## 变化与已确认结论
...

## 接收方任务
- ...

## 必须保持
- ...

## 验收标准
- ...

## 参考
- ...

````
`参考` 可指向接收方能够访问的 Spec、API、任务、代码或提交。

独立上下文中，正文不得依赖这些引用才能理解任务；共享工作区中，可以用引用代替已经存在的详细事实。

## 生命周期

发送方生成 Handoff
→ 接收方读取并执行
→ 稳定结论写入正式工件
→ 验收完成后删除 Handoff

`HANDOFF.md` 是临时交接入口，不应长期保留造成重复执行。
